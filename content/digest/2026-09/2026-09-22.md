## D1 — Agentic Engineering

**Specification frames beat instruction files for LLM-generated code correctness.** A [pre-registered, five-model paired evaluation](https://arxiv.org/abs/2609.23270) tested a 267-word specification preamble on 50 backend tasks across finance, healthcare, and insurance. Nine deterministic AST-based checkers and the Bandit security scanner agree: the frame reduced defects in all five models, with the frame arm winning 95 of 100 divergent comparisons and never making any model worse. The Bandit scanner found 53 medium-or-high issues bare vs. 11 with the frame. The key insight for D1 practice: the effect is largest where a model's unprompted defaults are weakest — the spec supplies discipline the model lacks. This is directly actionable in any agentic coding pipeline. *(Cross-cutting: D4 — fewer defects mean fewer downstream incidents.)*

**CodeMidas turns existing codebases into RL training environments using source code alone.** The [CodeMidas pipeline](https://arxiv.org/abs/2609.22068) allocates agentic compute to explore implemented functionality, formulate behavioral specifications, construct execution-grounded tests, and validate through repeated rollouts. The resulting dataset spans 5,545 tasks across 3,185 repos, 23 languages, and 15 domains. Training MiMo-V2.5 with GRPO yields +11.7% on DeepSWE, +17% on ProgramBench, and +8.5% on Terminal-Bench. The trajectory analysis finding is notable: RL-trained agents explore codebases more broadly and self-verify more diversely. This is the agentic factory improving itself — agents building better training data for agents.

**EvoPilot demonstrates human-gated agentic research loops over 37 days in production.** The [EvoPilot system](https://arxiv.org/abs/2609.21257) runs role-specific agents through versioned domain skills with typed adapters for long-horizon online experimentation. A primitive autoresearch attempt incorrectly attributed a 22-percentage-point hit-rate decline to a model head; EvoPilot's verification layer traced it to a pre-existing evaluation defect (output depths of 3,000 vs. 600). After repair, the real improvement was 3.20 percentage points. Durable state recovered an interrupted round and artifact reuse saved ~5 GPU-hours. The lesson: unverified agentic loops in production systems can produce confidently wrong conclusions that influence product decisions. *(Cross-cutting: D4 — verification overhead pays for itself by preventing costly wrong-direction optimization.)*

**Agentic reverse engineering generates Business Requirements Documents in minutes, not months.** A [seven-agent framework](https://arxiv.org/abs/2609.22719) autonomously discovers user journeys, extracts business rules, and synthesizes locked BRDs from code, tests, config, and documentation. On a real enterprise deployment, it generated comprehensive BRDs in under 9 minutes per service, with rules corroborated against production defect records. Against a prior migration to the same target architecture that took over 2 years, the framework claims >98% cost reduction using IFPUG complexity models. Even discounting the headline number, the pattern — agents extracting formal specs from undocumented legacy code — is a critical enabler for migration programs. *(Cross-cutting: D4 — directly attacks tech debt cost; SCE — machines generating the blueprints that were never drawn.)*

**ReAgent audits agent-written research for artifact consistency.** The [ReAgent framework](https://arxiv.org/abs/2609.22111) combines static and dynamic auditing to verify that agent-generated research documents are backed by their code and experiments. It catches hard-coded metrics, unimplemented methods, and cases where experiments reproduce reported numbers while deviating from claimed methodology. As agentic engineering increasingly produces its own documentation and research artifacts, automated consistency auditing becomes a necessary verification layer. *(Cross-cutting: SCE — this is inspection for agentic output.)*

## D2 — AI in the Product

**Governance-aware agentic digital twin for power grid control rooms.** A [system for transmission grid operators](https://arxiv.org/abs/2609.22476) constrains the LLM to selecting and parameterizing whitelisted analysis tools, with a governance layer enforcing four inviolable rules: whitelisted-only execution, step budgets, explicit operator approval for side effects, and backend-rendered numerics with units and provenance. Across 590 runs, tool selection hit 96.5% and task success 93.7%, with all four governance rules holding without exception. Removing the layer caused the model to execute all 45 approval-requiring runs without authorization. The enforcement overhead is 12-16ms per request. This is a template for deploying agents in safety-critical product contexts where "human on the loop" must have teeth. *(Cross-cutting: D1, D4 — governance-by-construction prevents incidents.)*

**Specification frames improve product-facing code generation.** The [specification frame study](https://arxiv.org/abs/2609.23270) tested on tasks directly relevant to product backends — money arithmetic, time handling, retry safety, and access control. These are exactly the defect classes that create support tickets and incidents in production financial and healthcare systems. The frame's effectiveness across all five vendor lineages means it's model-agnostic and can be embedded in product-facing code generation features without vendor lock-in.

## D3 — Build for Agents

**The Agent Plugin ecosystem has a composition problem, not a packaging problem.** An [analysis of 68,072 plugin bundles](https://arxiv.org/abs/2609.23809) across 30,655 repositories finds only 6.2% validate against the Agent Plugins v1.0.0 specification, but the conformance gap is shallow (96.6% would load with one missing field). The real problem: 81% of capability-exporting bundles share a name with another plugin, with no namespace or precedence rule. The paper identifies four concepts the standard must add: qualified capability identity, declared capability surface, precedence rules, and inter-plugin relations. For anyone building B2A or agent interoperability surfaces, this is a clear warning: don't assume plugin portability exists yet, and don't build composition strategies on the current standard without your own namespace scheme.

**Authorization revocation formalized for long-running agents.** A [theoretical framework](https://arxiv.org/abs/2609.21284) defines "root-scoped authorization quiescence" — proving that when you revoke an agent's credentials, all downstream delegated tasks, queued callbacks, and provider-side operations actually stop or rebind. The protocol handles delegated tasks, shared work with independent authorization, and crash/replay stability. A provider-free test suite matches 17/17 registered outcomes and rejects 44/44 semantic regressions. While highly theoretical, this addresses a real operational gap: long-running agents that outlive their initiating processes through delegated credentials are a growing security and compliance concern. *(Cross-cutting: D4 — prevents the "zombie agent" class of incidents.)*

## D4 — Cost of Ownership

**Memory injection is a hidden, growing cost line item in multi-agent workflows.** The [Total Cost of Agency (TCA) framework](https://arxiv.org/abs/2609.23790) decomposes multi-agent workflow cost into base prompt, inference, memory injection, miss penalty, and context-accumulation components. On a 200-task enterprise benchmark against real model APIs, memory injection accounts for ~12% of total billed cost, rising from zero at depth one to 27.6% at depth six. Growth is linear with depth (R²=0.9974). Critically, production observability tools currently don't separate tokens a node generates from tokens it receives — this cost is invisible to the teams paying it. Reducing retrieval window capacity from 32 to 2 entries lowered injected tokens by 28.7% with accuracy change within seed-level variation. This directly threatens the ½× downstream cost equation: teams scaling to deeper agent graphs will see token costs rise linearly with architectural depth unless they actively manage context injection.

**Formal verification catches 25-50% more defective patches than test suites.** The [SWE-Proof benchmark](https://arxiv.org/abs/2609.21190) applies formal verification to 500 real SWE-bench issues and finds that a quarter to a half of test-passing patches admit counterexamples. A correct formal specification lifts resolution from 85% to 95% for Opus 4.8. But models that must write their own specs gain nothing over baseline — only 62% of model-written specs pass audit, with the usual failure being "faithfulness" (constraining part of the behavior, leaving the rest free). This means agentic pipelines shipping test-passing but formally unsound patches are accumulating latent defects that will surface as production incidents. The specification synthesis gap is the bottleneck.

## Software Civil Engineering Lens

Today's batch is remarkably concentrated on the SCE thesis — five of twelve items directly advance or evidence it.

**The specification-before-generation result is the most significant SCE evidence this quarter.** The [pre-registered study](https://arxiv.org/abs/2609.23270) demonstrates empirically what SCE predicts theoretically: a formal specification preamble — a "blueprint" — systematically improves code quality across all models and all domains tested. Instruction files (informal guidance) showed no benefit in the largest prior study; specifications (formal constraints) showed universal benefit. This is the difference between telling a builder "be careful with the wiring" and handing them an electrical code. The 267-word frame maps almost perfectly to the SCE "codes/norms" pillar.

**SWE-Proof reveals the specification gap as the binding constraint on professionalization.** The [finding that models can't write faithful specs](https://arxiv.org/abs/2609.21190) — only 62% pass audit, with the failure mode being partial behavioral coverage — is a precise measurement of where we are on the SCE maturity curve. We can verify specs mechanically (simulation/inspection capability exists), but we can't generate specs reliably (the "blueprint" pillar is human-dependent). This is the "10% → 10×" boundary: human judgment is still required at the specification level, and relocating it there is exactly the "human on the loop" transition SCE predicts.

**VSpector's specification-driven CPU bug detection is SCE in hardware.** While [VSpector](https://arxiv.org/abs/2609.23517) targets RISC-V CPUs rather than software, the pattern is pure SCE: take a natural-language specification, extract verifiable rules, check implementations against them, find 42 previously unknown bugs that fuzzing couldn't find. The four-stage pipeline (rule extraction → implementation localization → candidate identification → violation auditing) is a concrete instance of the Specify → Verify lifecycle.

**The agentic BRD generation framework is reverse-SCE**: building the blueprints from the building. The [code-to-requirements pipeline](https://arxiv.org/abs/2609.22719) addresses the most common real-world gap — systems built without specs. If agents can reliably extract formal specifications from existing code, the professionalization pathway doesn't require starting from greenfield. Legacy systems can be retroactively "blueprinted."

**The governance-aware digital twin is bounded autonomy made concrete.** The [power grid system](https://arxiv.org/abs/2609.22476) implements exactly what SCE prescribes: agents operate within spec constraints (whitelisted tools, step budgets), with human approval gates for side effects, and full audit trails. The 96.5% tool selection accuracy with 100% governance compliance demonstrates that bounded autonomy is achievable at useful performance levels. The 12-16ms enforcement overhead shows the cost of professionalization is negligible compared to the cost of ungoverned operation.
