## D1 — Agentic Engineering

**AWS ships an agent-built emulator for local service testing.** The [aws-emulator](https://simonwillison.net/2026/Nov/11/aws-emulator/) is the first official AWS tool for running tests against a local clone of AWS services without paid API keys. What makes it a D1 landmark: it was written in Rust by a "huge swarm of agents" producing 29,684 commits in three weeks. Swami Sivasubramanian's [blog post](https://simonwillison.net/2026/Nov/11/aws-emulator/) describes the orchestration approach. The project itself is a test infrastructure artifact, but the meta-story — a major cloud vendor using agent swarms to ship a Rust codebase at this velocity — is the most concrete public evidence yet that agentic engineering at scale is moving from experiment to production-grade output. (Also D4: dramatically reduces the cost of AWS integration testing.)

**Anthropic reveals Mythos ported Claude to AMD GPUs in three days.** In their [IPO roadshow video](https://simonwillison.net/2026/Nov/11/anthropic-ipo-roadshow/), co-founder Tom Brown disclosed that bringing up a new chip platform previously required "dozens of engineers months of work," but Mythos (Claude's internal agent identity) wrote or ported "almost 100% of the kernels" to AMD with "basically no human intervention." This is a rare first-party attestation of an AI agent performing complex systems engineering autonomously. Anthropic also introduced the concept of "compute multipliers" — algorithmic efficiency gains that compound — and explicitly stated their belief that Claude will eventually discover these multipliers "entirely by itself," a recursive self-improvement thesis with direct implications for inference cost trajectories. (Also D4: if multipliers compound as claimed, inference costs for Claude consumers will drop non-linearly.)

**JioHotstar benchmarks six retrieval approaches for AI coding agents.** [Their evaluation](https://www.infoq.com/news/2026/11/jiohotstar-codingagent-retrieval/?utm_campaign=infoq_content&utm_source=infoq&utm_medium=feed&utm_term=AI%2C+ML+%26+Data+Engineering) across SWE-bench, CodeScale Bench, and an internal QA harness found that structural search outperforms on concrete, well-specified tasks while semantic retrieval wins on ambiguous requirements. The practical takeaway for agentic engineering pipelines: knowledge-base tool selection should be task-type-aware, not one-size-fits-all. This aligns with the emerging pattern of context engineering as a first-class discipline — the retrieval strategy you choose is as important as the model you invoke.

**OpenAI demonstrates voice-steered Codex at AI Engineer Code Summit.** At the [AIE Code Summit](https://latent.space/p/codex-work/), OpenAI showed developers steering Codex by voice, handing off work to cloud agents, and using "dots" (likely a new orchestration primitive). While details are thin in the available summary, the voice-steering pattern signals a shift in the human-agent interface: from typing prompts to spoken intent, which further compresses the feedback loop in agentic workflows.

**Holiday Extras turns domain expertise into agent-built apps.** [This OpenAI case study](https://openai.com/business/customer-stories/holidays-extras-codex) describes a travel company using Codex to translate customer-facing expertise directly into applications, claiming higher booking conversion. It's a lightweight but real example of non-engineering domain experts using agentic tools to build production software — the "citizen developer" thesis executed through agent intermediation rather than low-code platforms.

## D2 — AI in the Product

**Decision models become a three-vendor commodity.** Google launched [Gemini Decision 1](https://simonwillison.net/2026/Nov/11/gemini-decisions-api/), joining Jev and OpenAI in offering specialized decision model APIs that handle yes/no, choice, and rubric-scoring questions. Pricing has converged: Jev at 4.2¢/M input tokens, Google and OpenAI at 10¢/M, with output free across all three. Gemini differentiates by supporting text, images, audio, video, and PDFs — genuinely multimodal decision-making. For product teams, decision models are a new building block: they let you replace expensive general-purpose LLM calls with purpose-built classification at 10-100× lower cost, making previously uneconomical per-request AI decisions viable. (Also D3: the standardized question formats — yes/no, choice, rubric — are proto-interfaces for agent-to-agent decision handoffs.)

**"System One" models emerge as a distinct category.** The [Jev Revolution coverage from AI Engineer Code Summit](https://latent.space/p/jev-revolution/) positions Jev-style decision models as "System 1" — fast, cheap, automatic — versus reasoning models as "System 2." Glean and others showed production use cases. The conceptual framing matters: it gives product architects a vocabulary for decomposing agent systems into fast/cheap classifiers and slow/expensive reasoners, which is the architectural pattern that makes agentic products economically viable.

## D3 — Build for Agents

**Decision model API convergence creates a de facto interop standard.** With [three vendors](https://simonwillison.net/2026/Nov/11/gemini-decisions-api/) now supporting essentially the same question types (yes/no, choice, rubric), using the same terminology ("Noul"), and offering similar pricing structures, we're watching a machine-consumable API standard emerge organically. For B2A (Build for Agents), this means agents can treat decision-making as a swappable commodity — pick the cheapest provider for text, the multimodal one for video, and failover between them. The API surface is simple enough that an MCP tool wrapper is trivial.

**Google enters the decision model market with multimodal support.** The [Gemini Decisions API](https://simonwillison.net/2026/Nov/11/gemini-decisions-api/) extending decision models to video and audio inputs opens new agent consumption patterns. An agent processing a support call recording can now ask "Did the customer express frustration?" as a structured yes/no with calibrated probability, rather than transcribing and prompting a general-purpose LLM. This is a net-new capability for agent pipelines that no other decision model provider offers yet.

## D4 — Cost of Ownership

**ReTrace distills agent workflows to cut per-task cost 24% and latency 130×.** This directly advances the 2× output / ½× downstream cost equation: for repetitive SOP-based processes, [ReTrace](https://arxiv.org/abs/2611.14492v1) extracts the decision logic from logged agent runs into code-driven workflows that eliminate per-step LLM calls. On production data (79 procedures), completion rate drops only 3 percentage points (93.8% vs 96.8%) while cost falls 24%. On τ²-Bench, latency drops from 170s to 1.3s. The architecture is clever: agent reasoning traces capture *why* each step was taken, not just *what* tool was called; these conditions get merged into a "rule document" that compiles to different orchestration platforms. Three rounds of repair on training failures lift quality above the original agent. This is the most rigorous evidence we've seen for the "train expensive, run cheap" pattern in agentic automation.

**Kiji Inspector exposes why agents select specific tools, enabling observability for agent decisions.** [Dataiku's open-source tool](https://www.infoq.com/presentations/explainable-ai-llm-agent-decisions/?utm_campaign=infoq_content&utm_source=infoq&utm_medium=feed&utm_term=AI%2C+ML+%26+Data+Engineering) uses Sparse Autoencoders applied to decision tokens to move beyond chain-of-thought narratives into causal understanding of agent tool selection. For incident management and 2nd/3rd-line support, this is significant: when an agent makes a bad tool call in production, you need to understand *why* at the mechanistic level, not just read its self-reported reasoning. The approach — layer activation extraction via patched vLLM engines plus causal ablation — is technically demanding but addresses a real gap in agent observability that otherwise shows up as undiagnosable production incidents.

**Google's TPU Sync reduces inference infrastructure costs.** [TPU Sync](https://www.infoq.com/news/2026/11/google-tpu-sync/?utm_campaign=infoq_content&utm_source=infoq&utm_medium=feed&utm_term=AI%2C+ML+%26+Data+Engineering), a C++ library for moving KV cache blocks and model weights between TPU HBM, host DRAM, and network storage, directly attacks inference cost by improving hardware utilization. Combined with Anthropic's "compute multipliers" thesis, infrastructure-level optimizations like this represent the supply-side cost reduction that makes the agentic factory's token economics more sustainable over time.

## Software Civil Engineering Lens

Today's items converge on a striking theme: **the professionalization of agentic output is happening faster on the infrastructure side than the application side.**

The **aws-emulator** story is the most SCE-relevant: a codebase of nearly 30,000 commits written by agent swarms is now part of AWS's official test infrastructure. This raises immediate questions about the SCE "codes and norms" pillar — who reviews 30,000 agent-generated commits? What's the equivalent of a structural inspection? AWS presumably has answers (their reputation depends on it), but the methodology isn't public. This is exactly the gap SCE predicts: the capability to generate at scale arrives before the inspection and certification frameworks to ensure what's generated is sound.

**ReTrace** is the most SCE-aligned research of the day. It follows the Specify → Plan → Verify → Apply → Observe lifecycle almost exactly: SOPs are the specification, agent traces are the plan, rule extraction is verification, workflow compilation is application, and the repair loop is observation feeding back. The insight that reasoning traces contain *why* (conditions), not just *what* (tool calls), maps directly to the Event Modeling thesis — the "why" is the domain logic that belongs in the blueprint, and ReTrace automates extracting it. This is a concrete mechanism for moving from "human in the loop" (agent decides every step) to "human on the loop" (human validates the extracted rule document, then code runs autonomously).

**Geoffrey Huntley's talk** — ["The Answer to AI is Engineering"](https://ghuntley.com/answer/) — is the most direct invocation of the SCE thesis we've seen from a practitioner stage. His argument that Nix overlays let you "patch the whole world," combined with property-based testing and back-pressure loops, maps to the SCE pillars of material datasheets (Nix as reproducible dependency specification), simulation (property-based testing as structural simulation), and codes/norms (back-pressure as a safety mechanism against unbounded agent autonomy). The title itself — "the answer to AI is engineering" — is essentially the SCE thesis in five words.

**Kiji Inspector** contributes to the "simulation" pillar by enabling causal analysis of agent decisions. If you can mechanistically explain *why* an agent chose a tool, you can build test harnesses that verify decision quality without running full end-to-end agent traces. This is the "terraform plan for domain logic" concept applied to agent behavior: inspect the plan before you apply it, at the neuron level.

The decision model convergence (Jev/OpenAI/Google) is worth watching through the SCE lens too. Standardized decision APIs with calibrated probabilities look a lot like material datasheets — known properties, tested under standard conditions, with quantified confidence intervals. When three vendors agree on the same question types and return calibrated probabilities, you have something approaching a specification standard for AI judgment, which is a prerequisite for the "codes and norms" pillar.
