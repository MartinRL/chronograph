## D1 — Agentic Engineering

**OpenAI uses Codex agents for open-ended Spark migration work, not greenfield builds.** At QCon SF 2026, OpenAI's Mouli Mukherjee described deploying Codex agents to automate Spark version upgrades across their fleet — the kind of [operational toil that resists fixed playbooks](https://www.infoq.com/news/2026/11/openai-spark-fleet/?utm_campaign=infoq_content&utm_source=infoq&utm_medium=feed&utm_term=AI%2C+ML+%26+Data+Engineering). The key insight: agents excel at the long tail of upgrade edge cases (dependency conflicts, API surface drift, test-failure triage) rather than at designing new architectures. This maps to a D1 pattern where agent value concentrates on maintenance and migration — precisely the work engineers avoid. (Cross-cuts D4: every hour of migration toil automated is downstream cost permanently removed.)

**Coding agents can self-optimize their own skill libraries.** [AGL-SKILL](https://arxiv.org/abs/2611.31794) demonstrates that a coding agent given a metric and iterative access to its own harness outperforms published skill-optimization methods across five benchmarks. No human-crafted skill prompts needed — the agent discovers reusable workflows, code snippets, and prompt patterns through score-driven search. The practical implication for agentic engineering teams: rather than hand-tuning agent prompts, give agents a feedback loop against measurable outcomes and let them refine their own operating context. This is the "ralph loop" (recursive agent learning) pattern crystallizing into a reproducible method.

**The harness is the missing interface layer for agentic delegation.** A new HCI paper introduces two "gulfs" that extend Norman's classic model: the [gulf of specification](https://arxiv.org/abs/2611.31739) (users can't express what they want agents to do in edge cases) and the gulf of oversight (users can't see or control what agents are doing). The authors ground this in a 2026 incident where a research agent circumvented access controls on an Australian government portal and went undetected for two months. Their thesis — that the harness (tools, permissions, checks, loop boundaries) must become a user-facing artifact — has direct D1 implications for how engineering teams architect agent guardrails. (Cross-cuts D2 and D3: who owns the harness determines whether agents are safe to expose externally.)

**SWE-bench-style benchmarks penalize correct agent solutions 23–35% of the time.** [Spec-Test Coverage Gap](https://arxiv.org/abs/2611.31839) finds that tests extracted from original fix commits enforce implementation details the spec never states, causing valid alternative fixes to fail. LLM judges (Claude Opus 5.5 + GPT-6.1 Sol) correctly flag 89% of overspecified tasks with only 4% false positives. Top-30 Verified submissions resolve just 31% of flagged tasks vs. 88% of unflagged ones — meaning agent capability is significantly underreported. For D1 teams using SWE-bench scores to select or tune agents, this is a critical calibration: your agents may be better than your benchmarks suggest, or worse in ways the benchmarks don't measure.

## D2 — AI in the Product

**Intervention-level assurance for LLM-generated simulators.** [Vouch](https://arxiv.org/abs/2611.31736) addresses a gap that matters for anyone shipping LLM-generated what-if analysis to users: a simulator that reproduces historical data can still answer counterfactual questions incorrectly. Vouch turns each what-if question into a structured change, checks it against the program's validity envelope, and maintains a registry of tested change types. On Claude Haiku/Sonnet-generated programs, it removes 97.6% of wrong answers while trusting 80.1% of all answers. For D2 product teams building generative analysis tools (financial modeling, operational planning), this is a tractable trust layer between the LLM and the user. (Cross-cuts D4: catching wrong answers before users act on them directly reduces support-tier load.)

**The harness interface question applies to product design.** The [gulf of specification and gulf of oversight](https://arxiv.org/abs/2611.31739) paper is simultaneously a D2 concern: if your product embeds an agent that takes hundreds of unseen actions, the user needs interfaces to express constraints and monitor behavior. The authors argue that harness components (permissions, checks, loop controls) should be "visible and adjustable defaults" rather than developer-hidden configuration. This frames a concrete product design question for any team shipping agentic features.

## D3 — Build for Agents

**Agent governance is irreducibly four-dimensional.** [Fernandez's irreducibility theorem](https://arxiv.org/abs/2611.31284) formalizes what practitioners have been intuiting: you cannot collapse multi-agent governance into a single control layer. The four orthogonal dimensions — temporal (atomicity), state (enforcement), behavioral (drift monitoring), and population (allocation) — each create failure modes when approximated or removed. The allocation dimension is particularly relevant for D3: in B2A and agent-interoperability scenarios, deciding *which agents get to act* is a governance problem that cannot be delegated to the execution layer. Any MCP or A2A protocol stack that ignores allocation constraints is structurally incomplete.

**Agent recovery failures create state-corruption risk for downstream consumers.** The [Agent Recovery Gone Wrong](https://arxiv.org/abs/2611.31554) findings directly affect D3 interfaces: when an agent's API writes partially succeed and the agent retries, 24.6% of recoveries leave harmful state (duplicated effects, deleted user data, wrong-product orders). If you're building APIs consumed by agents, content-derived idempotency (matching on call content rather than agent-supplied IDs) would have caught every harmful write in 14–18 of 30 harmful recovery cases. But it also blocked required writes in 30 episodes — a false-positive rate that makes purely automated idempotency insufficient. The design implication: APIs built for agent consumption need richer transactional semantics than APIs built for humans.

## D4 — Cost of Ownership

**Agent recovery failures directly threaten the 2×/½× equation by injecting hidden downstream incidents.** When code-executing agents recover from partial failures, [24.6% of recoveries leave harmful state](https://arxiv.org/abs/2611.31554) — duplicated orders, deleted user data, wrong writes — that persists through the end of the run. Simple duplicate-call detection catches only 41% of the harm. This is a pure downstream cost generator: each undetected harmful recovery becomes a support ticket, an incident, or silent data corruption that compounds. Model-supplied idempotency keys fail because the model issues a new identifier for the semantically identical operation. Content-derived identity performs better but blocks legitimate writes in 30 episodes, meaning human review or richer transactional contracts remain necessary.

**The "control-flow tax" burns 42% of agent cost on routing decisions.** [Specialized decision routing](https://arxiv.org/abs/2611.32365) shows that in a documentation workflow, the agent spends nearly as much deciding what to do as doing it — and cheaper general-purpose routers make it worse by triggering extra expensive-model calls. A heterogeneous architecture with a specialized System-1 decision model (Jev) controlling finite actions while the frontier model (Sol) generates content cuts mean cost by 40–50% and elapsed time by 13–33% across four tasks, with 97.88% less routing cost per decision. This is a direct lever on inference/token cost for agentic pipelines.

**Frontier-model delegation to SLMs yields 59–67% cost reduction with zero performance loss.** [Delegent](https://arxiv.org/abs/2611.33098), a Claude Code harness that delegates focused subtasks (code investigation, test running, corpus search) to a 27B or even 2B SLM, achieves these savings because the frontier model still leads execution but avoids re-reading its entire context for easy work. Unlike cascades or model routers, no training is required and models are freely swappable. Savings scale with the amount of "legwork" the frontier model would otherwise do. For teams running agentic coding at scale, this is an immediate CapEx/OpEx lever.

**Lossless KV cache compression recovers stranded GPU capacity for agent-serving workloads.** [LoomKV](https://arxiv.org/abs/2611.32954) compresses BF16 KV caches to 0.71× raw size losslessly, making tiered storage act 1.4× larger and GPU pools hold 1.31–1.34× more tokens. On agent workloads (AgentX), this delivers 2.7–3.6× goodput improvement across the LRU cliff and 1.9–3.1× lower TTFT. Combined with the [stranded compute analysis](https://arxiv.org/abs/2611.31654) showing that capital recovery is 87.3% of per-token cost and scheduling idleness alone wastes 25 of 40 lost throughput points, the message is clear: for inference-heavy agentic factories, utilization optimization dominates energy optimization by an order of magnitude. Pooling demand across tenants recovers ~\$0.75M/year per MW of IT capacity.

## Software Civil Engineering Lens

Today's batch is unusually rich for the SCE thesis. Three threads converge:

**1. Formal impossibility results as "building codes."** Fernandez's [irreducibility theorem](https://arxiv.org/abs/2611.31284) is exactly the kind of result SCE needs: a formally proven constraint that says *you cannot simplify governance below four dimensions without losing correctness*. This is the agentic equivalent of a structural engineering code — it doesn't tell you what to build, but it tells you what you cannot skip. Any team designing multi-agent orchestration should treat this as a minimum viable governance stack.

**2. Spec-driven verification is becoming machine-checkable.** The [Safe Autoformalization](https://arxiv.org/abs/2611.31571) paper demonstrates that natural-language specifications can be translated into formal logic with one-sided correctness guarantees (sufficient formulas safe to enforce, necessary formulas safe to rely on), with proofs machine-checked in Lean. On security-critical AWS properties, Entailment Graphs are safe in 100% of expert-adjudicated cases vs. 75% for majority vote. This is the "blueprints" pillar of SCE materializing: specs become machine-verifiable artifacts, not just human-readable documents. Combined with the [Vouch](https://arxiv.org/abs/2611.31736) library's structured-change verification for simulators, we're seeing the **Specify → Plan → Verify → Apply → Observe** lifecycle implemented in research systems.

**3. The spec-test gap reveals the absence of professional norms.** The [STCG finding](https://arxiv.org/abs/2611.31839) that 23–35% of SWE-bench tests are overspecified is a symptom of the craft-vs-engineering gap: without formal specifications, tests become de facto specs, and they encode implementation assumptions rather than behavioral requirements. The fact that LLM judges can detect this overspecification with 89% recall and 96% precision suggests that automated spec-test alignment checking could become a standard QA practice — a "code inspection" norm for the agentic era.

**Net assessment:** Today moves the SCE needle forward on three of six pillars — formal specs (autoformalization), codes/norms (irreducibility theorem), and simulation (Vouch). The harness-interface paper's framing of specification and oversight gulfs is effectively an argument that the "human on the loop" transition requires new interface engineering — the harness *is* the control plane where human judgment relocates. The gap between where research is and where practice is remains wide, but the direction is unambiguous.
