## D1 — Agentic Engineering

**Parallel subagents are mostly cost, not quality.** A rigorous empirical study comparing single-agent vs. multi-subagent coding on repository construction tasks finds that [parallel subagents raise pass rates by only 1–5 percentage points at up to 3.8× cost](https://arxiv.org/abs/2611.33893). The study identifies three mechanisms where subagents actually help — self-checking, fresh context, and modularity — but crucially shows that a single-sentence prompt telling the agent to "probe the reference program first" recovers most of the self-checking gain at a fraction of the cost. From GPT-5.6 Sol to GPT-6.1 Sol, the subagent advantage shrinks as single agents learn to self-check. The practical takeaway: periodically resetting an agent's conversation context outperforms letting it grind in a long session. This directly challenges the "throw more agents at it" instinct many teams have adopted.

**VibeServe: agents building their own infrastructure.** [VibeServe](https://arxiv.org/abs/2605.06068) flips the typical agentic coding narrative from "agents write application code" to "agents write systems infrastructure." Its outer/inner loop architecture — plan system designs, implement candidates, check correctness, benchmark — produces LLM serving stacks that match vLLM and SGLang on standard workloads and deliver [2.3× the goodput of tuned SGLang for a 397B MoE model on AMD MI300As](https://arxiv.org/abs/2605.06068). The key insight is that bespoke systems exploit hardware- and workload-specific opportunities that generic stacks miss. This is D1 (agentic engineering of infrastructure) with strong D4 implications — if agents can build serving systems tailored to your exact deployment, the cost of running inference drops materially.

**SmartLens brings attribution and risk signaling to the IDE.** [SmartLens](https://arxiv.org/abs/2611.34377), an IntelliJ plugin, attributes code changes to agents vs. developers and surfaces three signals: skills the developer hasn't used before (learning), review priority ranking (understanding), and hotspot risk (files that change often, are mostly AI-written, and poorly understood by the developer). Across 8 OSS repos, agents introduced [up to 253 skills absent from the developer's own commit history](https://arxiv.org/abs/2611.34377). The risk ranking predicted bug-fix locations as well or better than plain churn. This is essential tooling for the "developer as manager of agents" paradigm — you can't review what you can't attribute. (Cross-cuts D4: the risk signal directly addresses downstream maintenance cost.)

**Agentic model checking: "agents propose, solvers verify."** [BMC-Agent](https://arxiv.org/abs/2605.21434) wraps a bounded model checker with an LLM agent that infers function specifications, configures verification tasks, decomposes analysis via specification-constrained stubs, and iteratively refines specs when counterexamples prove spurious. It [discovers confirmed defects in heavily tested, OSS-Fuzz-hardened libraries](https://arxiv.org/abs/2605.21434) without manually written specifications. The separation of concerns — semantic reasoning by agents, formal checking by solvers — is a template for how agentic engineering should handle verification at scale.

**Black-box test selection cuts agent evaluation cost by ~80%.** [The first empirical study of black-box test case selection for agentic systems](https://arxiv.org/abs/2611.34617) shows that Category Partition selection can reduce SWE-bench evaluation from 500 to 100 tasks ([\$225 → \$47](https://arxiv.org/abs/2611.34617)) with only 0.8pp estimation error on success rate. LLM-as-judge selection is better for early failure detection, finding [nearly twice as many failures as random sampling](https://arxiv.org/abs/2611.34617). For teams running continuous evaluation of agent pipelines, this is an immediate cost multiplier.

## D2 — AI in the Product

**Agent-operated live simulations as a product interface.** An [MCP server for discrete element simulation engines](https://arxiv.org/abs/2611.33926) lets a general-purpose AI agent run, monitor, modify, and stop simulations while a human modeler works at the same console. In the case study, [20 of 21 automated calibration sessions hit targets](https://arxiv.org/abs/2611.33926), with parameter sets converging to a small region of the admissible range. This demonstrates a "human on the loop" product pattern: the agent does the tedious parameter calibration while the domain expert retains full console access and visibility. The two open-source packages (itasca-mcp, yade-mcp) serve as a template for wrapping any simulation engine as an agent-accessible tool.

## D3 — Build for Agents

**MCP in engineering simulation: a real-world B2A pattern.** The [DEM simulation MCP server](https://arxiv.org/abs/2611.33926) is notable not just for its product implications but for its tool-design principles: correctness, coverage, orthogonality, and simplicity. The seven tools (2 documentation, 5 execution) represent a minimal but complete API surface for agent operation of a complex engineering tool. This is a concrete, production-quality example of making legacy software agent-consumable via MCP. (Cross-cuts D2.)

**Shared records for agent-to-business coordination.** IBM researchers present [Talea](https://arxiv.org/abs/2611.33373), combining signed AT Protocol records with A2A task execution for multi-party business commitments. The design study — an airline coordinating disrupted-passenger hotel bookings — surfaces real constraints: [confidentiality requirements restrict each hotel's view to its bilateral exchange](https://arxiv.org/abs/2611.33373), and deterministic release interfaces cannot bound disclosure when negotiated values depend on private state. This is early but important work on the trust and evidence layer that B2A (business-to-agent) interactions will require. The finding that shared records within a trust boundary improve decision reconstruction supports the case for standardized agent interaction records.

## D4 — Cost of Ownership

**Partial routing directly improves the 2× output / ½× cost equation.** Rather than routing entire tasks to cheap or expensive models, [partial routing](https://arxiv.org/abs/2611.33402) decomposes a single agentic task into subtasks and delegates suitable ones to a cheaper worker model. With δ=0.75, it [raises ViBench score from 70.2 to 78.5 while cutting cost 19%](https://arxiv.org/abs/2611.33402) — simultaneously better output and lower cost, the ideal D4 outcome. The approach requires no model training; it analyzes past runs to identify recurring subtask patterns and measures each model's quality/cost tradeoff on them. The practical implication: any team running multi-step agentic workflows should be profiling subtask difficulty and routing accordingly.

**Static analysis alone creates a false sense of safety in AI-generated code, inflating downstream incident risk.** [VULBENCH-CPP](https://arxiv.org/abs/2607.00107) benchmarks 8,918 C++ programs across human and LLM authors with four verification tiers. The critical finding: under static analysis, AI and human code look equally safe. But with dynamic analysis (ASan/UBSan), [LLM-generated code is roughly twice as likely to trigger confirmed runtime violations](https://arxiv.org/abs/2607.00107). Bounded model checking disagrees with sanitizers on direction, flagging human code more. No single verification tier is sufficient. For teams shipping agent-generated code, this means static-analysis-only CI pipelines are under-detecting real defects — the downstream incident cost is hidden until runtime.

**20% of LLM-generated industrial control scripts target the wrong controller.** [Proteus-OT](https://arxiv.org/abs/2611.33227) finds that [180 of 883 generated PLC scripts (20.4%) import packages mismatched to the declared industrial target](https://arxiv.org/abs/2611.33227), and 96.6% of those mismatches pass existence checks — the imports are real packages calling real methods, just for the wrong hardware. This is a novel class of downstream defect: code that compiles, passes linting, but would fail or cause harm when deployed to the actual physical system. For any team using LLMs to generate infrastructure or IoT code, vendor-protocol verification must be added to the pipeline.

## Software Civil Engineering Lens

Today's batch is unusually rich for the SCE thesis. Three papers directly address the gap between "code that runs" and "code that's correct," which is the core of software's professionalization challenge.

**The verification tier hierarchy is a "material datasheets" problem.** [VULBENCH-CPP](https://arxiv.org/abs/2607.00107) demonstrates that different verification methods disagree on which code is defective — static analysis says AI and human code are equivalent, dynamic analysis says AI code is 2× worse, and bounded model checking flags human code more. This is exactly analogous to civil engineering's realization that you need multiple, independent testing methods for structural materials. The paper's conclusion — "no single tier is sufficient" — is a direct argument for mandatory multi-tier verification standards (the "codes and norms" SCE pillar).

**Agentic model checking operationalizes "Specify → Plan → Verify → Apply → Observe."** [BMC-Agent](https://arxiv.org/abs/2605.21434) literally implements the SCE lifecycle: agents infer specifications (Specify), plan verification strategies (Plan), model-check bounded queries (Verify), and refine specs based on counterexamples (Observe). The "agents propose, solvers verify" principle is the clearest articulation yet of how to maintain formal guarantees while letting agents do the semantic heavy lifting. This is the "simulation before construction" pillar coming to life.

**LLM spec generation is still the bottleneck.** The [Coins framework](https://arxiv.org/abs/2608.13077) finds that [specification generation remains a "formidable challenge"](https://arxiv.org/abs/2608.13077) for LLMs, and that evaluation difficulty obscures genuine differences in spec quality. Similarly, [AutoformBench](https://arxiv.org/abs/2611.33165) shows that formalization success [depends less on mathematical domain than on models' ability to construct missing formal infrastructure](https://arxiv.org/abs/2611.33165) — definitions, intermediate lemmas, and supporting theory. These findings converge on a single conclusion: specification is where human judgment remains essential. The SCE model predicts exactly this — humans relocate to the spec layer ("human on the loop") while agents execute within bounded autonomy below it. We're not there yet; spec generation is the rate-limiting step.

**Vendor-protocol mismatches illustrate the "material datasheets" gap.** [Proteus-OT](https://arxiv.org/abs/2611.33227)'s finding that 20% of industrial scripts import valid-but-wrong packages is a perfect example of why software needs "material datasheets" — documented compatibility constraints that go beyond "does the library exist?" to "is this library appropriate for this target?" Civil engineering solved this decades ago with certified material-application matrices. Software hasn't.

**Net assessment:** Today moves the SCE needle forward on three of six pillars — codes/norms (multi-tier verification), simulation (agentic model checking), and material datasheets (vendor-protocol auditing). The formal specification pillar remains the acknowledged bottleneck. The gap between "code that compiles" and "code that's correct for its deployment context" continues to widen as agent-generated code volume increases — exactly the conditions that forced civil engineering's professionalization.
